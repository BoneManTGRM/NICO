# No-Server Assessment Mode

NICO can run local defensive assessments without exposing backend credentials to a browser session.

## GitHub repository assessment

```bash
python -m nico assess github owner/repo --authorized
```

or:

```bash
python -m nico assess github https://github.com/owner/repo --authorized
```

For private repositories, configure a local read-only GitHub credential in the `NICO_GITHUB_TOKEN` environment variable before running the command. Do not paste real credentials into documentation, screenshots, browser forms, or client reports.

The credential stays local. It is not exposed to the frontend.

## Project archive

```bash
python -m nico assess archive ./project.zip --authorized
```

Supported archive formats: `.zip`, `.tar`, `.tar.gz` and other tar-compatible formats.

NICO extracts the archive into a safe temporary directory and blocks path traversal attempts.

## Verification and exit status

`python -m nico assess verify latest` reports `verified` only when a completed
assessment report is available, its nonempty `scan_id` exactly matches the nested
local verification's `scan_id`, and that verification has `passed: true`.
A completed report with unsuccessful verification reports `verification_failed`;
an absent or incomplete report reports `no_assessment_report`. Both unsuccessful
verification outcomes print their JSON evidence and exit with code 1. Successful
verification exits with code 0.

New assessment JSON records the source `scan_id`. Verification JSON includes that
ID and an `assessment_scan_matches_verification` or
`assessment_scan_missing_or_mismatched` check. Reports without a scan identity
(including older reports and passive URL reports without a local scan) cannot
claim successful local scan verification. Rerun an authorized scan-backed
assessment to create a report with an identity. A different latest scan requires
its corresponding assessment report; matching only the target path is insufficient.

Authorization failures and caught assessment errors also print their structured
JSON and exit with code 1. The retrieval commands `assess latest` and `assess report
latest` retain their existing empty-result behavior and exit with code 0 only
when all three artifacts and the publication manifest are absent. This genuinely
empty state returns a plain-text message for report queries even when
`--format json` or `--format html` is requested.

### Complete report publication

Verification also requires `no_server_latest.manifest.json`, with matching
assessment/scan identities and SHA-256 hashes for the actual JSON, Markdown and
HTML bytes. Missing proof or missing, stale, or damaged artifacts fail closed;
the verification `checks` identify the artifact failure. Older reports without
this proof must be regenerated by an authorized assessment.

No-server publication takes an exclusive lock. On POSIX, verification and
retrieval hold shared locks across validation and reading; Windows serializes all
of these operations with a nonblocking one-byte exclusive lock. A competing
operation fails immediately with structured exception-type JSON and exit 1
(`BlockingIOError` on qualified Linux; Windows CRT errors may be `PermissionError`
or another `OSError`). Retry after the active operation finishes. The old
completion marker is removed before any artifact is overwritten. A new marker is
atomically replaced only after all three writes and report registrations succeed.
UTF-8 bytes are written directly, avoiding platform newline translation. These
separate file writes are not a filesystem-wide atomic transaction.

`assess latest` and `assess report latest` now require the same actual-byte
manifest integrity check while holding the lock. An orphan, stale, truncated,
missing-format, or legacy proof-less bundle returns structured
`ReportIntegrityError` JSON and exit 1 instead of serving partial content. Successful
JSON/Markdown/HTML content is unchanged. Report text is decoded from the exact
byte buffer whose hash was validated; it is not reread after validation. Retrieval checks publication integrity
only: it does not call scan verification, assert current-scan identity, or grant
human approval. `assess verify latest` additionally checks the nested scan result.

The implementation dispatches to POSIX `fcntl` or Windows standard-library
`msvcrt` with a fixed offset-zero, one-byte region for both acquire and release;
it never deletes stale lock files or runs unlocked. Linux local-filesystem behavior
is tested. The Windows branch has mocked contract tests only; real Windows
locking, process-exit cleanup and complete CLI qualification remain outstanding.
Unsupported platforms fail closed. No power-loss durability, distributed-filesystem
locking, protection against noncooperating writers or intentional alteration of
both reports and proof, or stable “latest” state after return is promised.

No-server scan verification now uses the selected scan's stored findings snapshot
and only repairs linked to that snapshot's finding IDs. Missing or malformed
snapshots fail closed. This does not establish an atomic snapshot across later
repair reads or concurrent scan writes.

No-server verification observes the nested scan result without persisting it as
an independent success. After artifact and identity checks it writes the sanitized
complete result to the audit log as `assessment.no_server.verification`, then
returns it. Audit failure prevents a success response. Existing shared verification
rows are not removed or rewritten. Consumers must use this audit event for the
no-server decision; the shared `latest_verification` result is not that decision.
The shared verifier's default global findings/repairs and persistence behavior is
retained for existing callers; scan scoping and non-persistence are explicit
no-server options, not a migration of all verification consumers.

No-server verification also opts into canonical SQL scan-row identity: the selected
row's nonempty ID must exactly match its JSON payload ID. JSON cannot overwrite
the canonical ID or attest its own validity. Inconsistent/absent identities fail
with `scan_row_identity_mismatch`; invalid JSON remains a sanitized CLI error.
Shared callers retain their original payload-merge behavior unless they opt in.

The scan observation is point-in-time: a valid report/scan A may verify if scan B
is committed after A was read, and a later invocation will observe B. Repairs are
read afterward and may reflect later metadata changes; they are not themselves a
pass criterion. No new cross-table snapshot transaction or global-latest-at-return
guarantee is introduced.
