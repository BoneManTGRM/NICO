# Dormant offline bundle and isolation plan — 2026-10-15

This additive change does not restore production TypeScript coverage. No scanner,
score, gate, flag, workflow, deployment or existing worker is modified. The runner
still rejects dependency/generated entries. There is intentionally no adapter that
turns a verified bundle into executable scanner authority.

## Verifier contract and supported subset

`typescript_offline_bundle_v1.verify_offline_bundle` accepts only in-memory bytes
and an independently supplied `BundlePolicy`. It performs no network acquisition,
filesystem extraction, package installation or execution.

The controller supplies an allowlisted Ed25519 public key, exact expected
repository/commit/tree/run/snapshot identity, compiler/library/Node digests,
authorized build workflow/revision/run/attempt, generator identity/config and
source inventory. These must NOT be copied from a target-provided envelope.

The signed statement binds those identities, the exact lockfile, full package and
generated inventories, and explicit completeness declarations. The verifier checks
actual source and generated bytes, the exact raw SHA-512 package archive integrity
from package-lock.json, package name/version, bounded extracted file inventories,
generator entry bytes and config bytes, and observed compiler identities. All
nonempty dependency declarations in the supported graph must resolve consistently.
A self-signed claim or a checksum without independent trust is insufficient.

Limits: at most 256 packages, 8 MiB compressed per archive, 32 MiB decompressed per
archive, 64 MiB compressed/package-content aggregate, 20,000 total package files;
source and generated maps each have a 64 MiB/20,000-file cap. Gzip expansion is
bounded before tar parsing. Duplicate paths/JSON keys, symlinks, hardlinks, special
files, extended tar metadata, traversal, source/dependency namespace conflicts and
generated/source overlaps are rejected. Archives are never extracted to disk.

The first supported lock subset is npm lockfile v3 with ordinary exact-version
registry dependencies. Ranges, aliases, links, workspaces, peer/optional/bundled
and OS/CPU/libc installation semantics are rejected rather than guessed. Generated
files must be UTF-8 .d.ts files under the generator config's .next/types directory,
include all controller-required paths, and match the complete signed inventory.

This restriction means NICO's real Next dependency graph is NOT supported yet.
Safe support for its actual npm resolution semantics and packaging metadata is a
separate step with owned controls; this draft must not be represented as the final
NICO offline type bundle. It creates no stubs, removes no missing declarations and
makes no claim of a successful type check.

The signature format is a controller-signed contract, NOT a GitHub/Sigstore
attestation verifier. No production signing key, trust store, artifact provenance
adapter or compiler-measurement adapter is installed by this change. A future
controller must authenticate the real build and artifact before issuing this
statement. The measured compiler argument must come from independently verified
image bytes, not an envelope field. A successful verification receipt explicitly
sets qualified_for_production=false and os_isolation_verified=false.

## Concrete dormant runtime plan

`typescript_isolation_profile_v1` returns a disabled specification and review-only
Docker arguments. There is no subprocess call, launcher, environment toggle,
workflow trigger or enable path. Edited/relaxed/enabled profiles are rejected.
The image reference must name assessment-typescript by immutable registry digest;
syntax validation is not image approval. --pull=never prevents implicit downloads
if an operator later uses the planned arguments.

Proposed single-container controls, not yet applied or qualified:

| Boundary | Proposed control |
| --- | --- |
| Filesystem | Read-only image root; no host mounts, checkout or Docker socket; stdin supplies frozen bytes; /work is a private 64 MiB tmpfs, uid/gid 10001, mode0700, nosuid,nodev,noexec |
| Network | Docker network=none; assert only isolated loopback and no outbound route inside the worker |
| Identity | uid/gid10001; all Linux capabilities dropped; no-new-privileges; assert effective caps=0 and NoNewPrivs=1 |
| Syscalls | Runtime-default seccomp; assert seccomp filtering active; no unconfined override |
| Processes | PID limit32; no child command execution by the fixed compiler entry point; nofile128; core dumps disabled |
| Memory | cgroup512 MiB, no additional swap; Node heap256 MiB; fail incomplete on OOM |
| CPU/time | 0.5 CPU quota; per-process CPU rlimit30 seconds; externally enforced60-second whole-container wall deadline |
| Storage/output | tmpfs64 MiB, stdout8 MiB, stderr32 KiB; no daemon logs; controller must bound all stdin/output and archive expansion |
| Authority | Fixed image-owned entry point; sanitized environment; no controller/API/registry credentials in target worker |
| Lifecycle | One worker at a time; forced container cleanup on completion, cancellation, timeout or capture failure; verify cleanup before credit |

Some controls above require the future controller/entry point (not Docker flags
alone): wall/output/input limits, environment allowlist, inside-container checks,
concurrency, immutable-image approval and verified cleanup. The current prototype
has a smaller15-second local wall deadline and is still owned-fixture-only. The
planned container budget is a proposal, not capacity qualification or a request
to increase any existing worker's resource limits.

## Observed capabilities and smallest service route

Read-only executor inspection found Docker CLI/socket access, cgroup v2, built-in
seccomp, and bwrap/unshare executables. `docker info` reported5 CPUs and
18,882,699,264 bytes daemon memory. The executor's cgroup reports CPU quota4,
memory17,179,869,184 bytes and unlimited PID count. These are observations, not
new worker grants. `docker image ls` returned no images. No container or namespace
was started, image downloaded, syscall policy applied or security setting changed.

The existing production worker workflow is a main-only authorized-job consumer on
GitHub-hosted ubuntu-24.04, using OIDC and a digest-checked tool-specific image.
Its container implementation already demonstrates the architecture for isolated
jobs. That existing tool-specific profile is NOT TypeScript qualification and will
not be repurposed or restarted by this draft. Railway runs the application image;
no live Railway Docker/socket or nested-isolation capability was inspected or
assumed. Vercel is not selected as an arbitrary scanner process host.

The smallest proposed deployment route uses the existing NICO GitHub Actions
service for a separate TypeScript-only job, a separately approved immutable Node/
TypeScript image, its own job identity/concurrency and retained bounded receipts.
It needs existing Actions compute and repository artifact/registry read access in
the controller; an image publication step, if required, needs packages:write only
in that producer. No new external service is proposed. Actual compute cost/capacity
is not approved by this plan. No additional spend is authorized.

No image digest/entry point or live boundary qualification exists yet, so there is
no concrete launch ready for approval. A future request must name that exact image,
job, owned fixture and bounded controls; it cannot be a general approval to enable
project commands. Publication of this dormant draft needs no additional permission.

## Existing-service route for NICO's offline type data

Prefer an already authorized NICO Node/Vercel build at the exact assessed source
SHA. First inspect only authorized build metadata and retained artifact manifests;
never use the blocked assessment report as an acquisition route. Require matching
source/lockfile hashes and the immutable build identity before reading bytes.

The inspected Node.js CI runs exact npm installation, TypeScript lint and Next
build, but uploads audit-results only. The production frontend proof retains JSON
release evidence; Phase9 retains scanner logs/manifest. These definitions do not
retain the required package archive bytes, complete extracted dependency inventory
and generated .next/types declarations. No actual build artifact was downloaded
or claimed present/complete in this step.

If an existing authorized build already retains all these bytes, a bounded
read-only exporter can gather them without rerunning scripts or installation.
Otherwise a collector attached to a future separately authorized normal NICO build
must export: source/lock identities, original package archives with verified SRI,
complete dependency file inventories, pinned compiler/library/generator identities,
and all generated .d.ts bytes with exact build provenance. Do not silently rerun
builds, fetch packages, synthesize Next declarations or weaken completeness.
